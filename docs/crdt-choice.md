# Phase 3 検討メモ: CRDT を自前実装するか、Automerge を使うか

- 状態: 検討中（決定したら design.md の決定ログへ転記）
- 前提となる用途: **ルールと設定の同期**。数十KB規模の小さなドキュメントを、2〜3ノード（自宅PC・遠隔mini PC）間で同期する。編集は人間起点で低頻度（1日数回以下）。オフライン編集→復帰時の自動マージが Phase 3 の完成定義。

## 比較表

| 観点 | ① 自前実装（LWW-Map + HLC） | ② Automerge |
| --- | --- | --- |
| 実装の初期コスト | CRDT本体 200〜300行 + 同期・ファイル橋渡し 300〜500行 + テスト。数日相当 | ライブラリと automerge-repo（WebSocket同期の既製品）で**半日〜1日で繋がる** ✅ |
| 依存・デプロイ | **依存ゼロ継続。mini PC へは `git clone` だけ** ✅ | npm 依存（Rust製コアの WASM バイナリ、MB級）。各ノードに npm 工程が増える |
| 正しさの実績 | 自作＝自分のテストが品質のすべて。**プロパティテスト**（ランダム順序でマージ→全ノード収束を機械検証）でかなり潰せるが、実績はゼロから | 学術ベースの実装・多数の本番利用。**マージの正しさを信頼して忘れられる** ✅ |
| マージの意味論（ルール用途） | ルール単位の LWW＝「どちらかの編集がそのまま勝つ」。**自動化ルールとしては予測可能で安全** ✅ | フィールド単位マージ＝両者の編集が混ざる。trigger は A の編集・action は B の編集という「誰もレビューしてないキメラルール」が生まれ得る（ルールを atomic な塊として扱えば回避できるが、それは Automerge の旨味を捨てる使い方） |
| 時計・因果関係 | wall-clock LWW は時計ズレに弱い → **Lamport/HLC（ハイブリッド論理時計）の自作が必要**（+50行程度） | actor ID と因果順で解決。**壁時計に依存しない** ✅ |
| 履歴・監査 | なし。ただし tsukumo にはイベントストアがあるので「同期・マージイベント」を流せば運用上は代用できる | **全変更履歴が構造として残る**（誰がいつ何を変えたか）。自動化ルールの監査ログとしては本来嬉しい ✅ |
| 同期プロトコル | 全状態交換（ドキュメントが小さいので十分。実装も単純） | 差分同期・断続的接続に強いプロトコルが付属。**ドキュメントが育っても効く** ✅（ただし今の規模では差が出ない） |
| 学び | **CRDT の法則（可換・結合・冪等）を自分の手で書いて証明する体験**。「CRDT楽しそう」の核心はこっち ✅ | API の使い方の学びが中心。内部を読む学びはあるが受動的 |
| この開発環境との相性 | **npm 遮断環境でも今この場で実装・テスト・E2E まで回せる** ✅ | この環境では動かせない（あなたの手元での作業になる。私はコードは書けるが実行検証できない） |
| 将来の拡張（リスト・テキスト・大きな doc・多ノード） | 必要になった時点で書き足すか、乗り換え | 最初から全部ある ✅ |
| 撤退コスト | 同期層はインターフェース分離済み（設計原則）なので、**どちらを選んでも後から差し替え可能** | 同左 |

## 補足: 実はもっと素朴な選択肢もある

2ノード・低頻度編集なら、rules ディレクトリを git リポジトリにして pull/push するだけでも実用上は回る（コンフリクトは手で直す）。ただし Phase 3 の完成定義（オフライン両側編集→**自動**マージ）と、このプロジェクトの動機（CRDT を学びたい）から、CRDT 本命で進める。

## 推奨: ① 自前実装（LWW-Map + HLC）

理由は3つ：

1. **用途に対して意味論が正しい。** ルールは「1個の編集単位」であり、フィールド単位で他人の編集と混ざるより、ルール丸ごと新しい方が勝つ（LWW）ほうが、家を動かす自動化としては予測可能で安全。Automerge の最大の強み（細粒度マージ）が、この用途ではむしろ要らない。
2. **依存ゼロと `git clone` デプロイが守られる。** 監視カメラを兼ねる遠隔 mini PC の運用的にも、デプロイが単純なのは効く。
3. **動機と環境に合う。** 「CRDT何それ楽しそう」の楽しさの本体は自分で書くことにあり、しかも npm 遮断のこの環境で今日から一緒に作って E2E まで検証できる。

自作の最大リスク（エッジケースの正しさ）は**プロパティテスト**で潰す：ランダムな操作列を生成し、任意の順序・重複・分断で交換しても全ノードが同一状態に収束することを機械的に検証する（可換性・結合性・冪等性のテスト）。

**Automerge に乗り換えるシグナル**（どれかが現実になったら差し替えを検討）：
- 変更履歴・監査が本当に欲しくなった
- リストやテキストなど順序つきデータの同期が必要になった
- ノードが5台を超えた／ドキュメントが MB 級に育った
